## Guiding Rule

**Every chunk leaves the app in a working, deployable state.** The original atha-family must be able to log in and use all features after every push. The `settings` table PK change is deferred until Chunk 5 (when the app is already scoped) to avoid a premature breaking change.

---

## Chunk 1 — DB Foundation

**What:** Schema migration only. Zero application code changes. Zero user-visible changes.

**Why first:** Everything depends on these tables existing. The migration adds `family_id` as *nullable* only — the running app ignores nullable columns it doesn't read, so nothing breaks.

**Files to create/modify:**
- `days-out-code/db/schema.ts` — add 4 new tables; add nullable `family_id` column to 7 existing tables
- `days-out-code/db/migrations/` — generated by `drizzle-kit generate` (runs in Docker builder)

New tables:
```ts
families          (id, name, slug, isActive, createdAt)
family_settings   (familyId PK FK, familyPinHash, adminPasswordHash, pinSessionVersion, updatedAt)
setup_tokens      (id, familyId FK, token, isUsed, createdAt, expiresAt)
setup_progress    (familyId PK FK, privacyAccepted, pinSet, activitiesCopied, membershipsSeen, completedAt)
```

Nullable FK column added to: `activities`, `memberships`, `family_memberships`, `votes`, `passport_stamps`, `wishlist_items`, `settings`

Migration sequence:
1. Add nullable `family_id` to all 7 tables
2. `INSERT INTO families (id, slug, is_active) VALUES (1, 'atha-family', true)`
3. Populate `family_settings` for family_id=1 via one-time script reading from `.env` (do NOT embed hashes in SQL file)
4. `UPDATE <each table> SET family_id = 1 WHERE family_id IS NULL`
5. Add composite indices per ADR-005 requirement 3

**Note:** `settings` PK stays as `key TEXT` for now — composite PK change deferred to Chunk 5.

**Before deploying:** Take a full `pg_dump` backup.

**Verify:** `SELECT COUNT(*) FROM families` → 1 row. `SELECT family_id FROM activities LIMIT 1` → 1. App works exactly as before.

## Chunk 2 — Operator CLI + Seed Refactor

**What:** Three CLI scripts and a seed function refactor. No app code changes. No user-visible changes.

**Files to create/modify:**
- `days-out-code/scripts/family-create.ts` — creates family row + setup token, prints full URL
- `days-out-code/scripts/family-delete.ts` — hard-delete all family rows, prints count per table
- `days-out-code/scripts/family-reset-password.ts` — updates `admin_password_hash` for a family
- `days-out-code/package.json` — add `family:create-setup-link`, `family:delete`, `family:reset-password` scripts
- `days-out-code/db/seed.ts` — refactor to export `seedActivities(familyId: number)`; existing top-level call passes `familyId = 1`

Reserved slug blocklist (enforced at registration, not middleware):
```ts
['api', '_next', 'health', 'pin', 'login', 'admin', 'setup', 'privacy', 'favicon', 'robots', 'sitemap']
```

Deletion order in `family-delete.ts`:
`passport_stamps` → `votes` → `wishlist_items` → `activity_memberships` (via JOIN) → `family_memberships` → `memberships` → `activities` → `settings` → `families` (CASCADE clears family_settings, setup_tokens, setup_progress)

**Verify:** `npm run family:create-setup-link -- --slug="test-jones"` → row in `families`, token in `setup_tokens`, URL printed. `npm run family:delete -- --slug="test-jones"` → rows removed, counts printed. Atha-family unaffected.

At this stage: `[slug]` pages render existing components, auth still reads from `.env`/old session, middleware attaches `x-family-id` header but nothing reads it yet.

## Chunk 4 — Auth Migration

**What:** Credentials move from `.env` to `family_settings`. JWT gains `familyId` and `pinSessionVersion`. Login forms on `[slug]` pages send `familySlug`. Rate limit keys become per-family-per-IP.

**Files to modify:**
- `days-out-code/lib/auth.ts` — rewrite credential providers: single joined query (slug → families JOIN family_settings); `familyId` + `pinSessionVersion` added to JWT; rate limit keys `pin:{familyId}:{ip}` / `admin:{familyId}:{ip}`; `jwt` callback validates `pinSessionVersion` for `role=pin` tokens
- `days-out-code/types/next-auth.d.ts` — add `familyId: number`, `pinSessionVersion?: number`; narrow `role` to `'pin' | 'admin'`
- `days-out-code/app/[slug]/pin/page.tsx` — hidden `familySlug` field (extracted from URL path client-side)
- `days-out-code/app/[slug]/login/page.tsx` — same

`authorize()` ordering (critical — see ADR-006 requirement 4):
1. Joined DB query by slug → if no row, return null (no rate limit charge)
2. Construct `pin:{familyId}:{ip}` key, check rate limit
3. `bcrypt.compare`
4. On match → return `{ id: familyId, role, familyId, pinSessionVersion }`

Old `/pin` and `/admin` become simple redirects to `/{atha-family}/pin` and `/{atha-family}/admin`. `.env` `FAMILY_PIN_HASH` and `ADMIN_PASSWORD_HASH` are no longer read by the app (retain in `.env.example` as documentation).

**Verify:** `/{atha-family}/pin` logs in, session contains `familyId: 1`. Create a second family with a PIN via direct DB insert; `/{slug}/pin` with that PIN works, session `familyId: 2`. Rate limit: 5 wrong PINs on atha-family → 429; other family PIN unaffected.

## Chunk 5 — Data Isolation

**What:** Every database query gains `WHERE family_id = session.familyId`. `settings` table PK changed to composite `(family_id, key)`. `NOT NULL` constraint applied to all 7 `family_id` columns.

**Files to modify:**

Child-facing APIs:
- `GET /api/activities` — filter by `familyId`
- `POST/GET /api/votes` — filter/insert with `familyId`
- `POST /api/passport` — insert with `familyId`
- `GET/POST/DELETE /api/wishlist` + `wishlist/[activityId]` — scoped
- All `activity_memberships` joins — anchor through `activities WHERE familyId = ?` (not a direct join)

Admin APIs:
- `POST/PUT/DELETE /api/activities` — set `familyId` on create; guard update/delete with `familyId` match
- `POST/PUT/DELETE /api/memberships` — scoped to `familyId`
- Admin dashboard aggregates — all counts filtered by `familyId`

Settings PK migration (second migration file):
```sql
ALTER TABLE settings DROP CONSTRAINT settings_pkey;
ALTER TABLE settings ADD PRIMARY KEY (family_id, key);
ALTER TABLE settings ALTER COLUMN family_id SET NOT NULL;
-- Also add NOT NULL to all other 6 tables in same migration
```

**Verify:** Browse as atha-family → 70 activities. Browse as test family (empty DB) → 0 activities. Admin dashboard counts correct per family. `SELECT COUNT(*) FROM activities WHERE family_id IS NULL` → 0.

## Chunk 6 — Onboarding Wizard

**What:** 7-step setup wizard at `/{slug}/setup`. First feature enabling families to self-onboard end-to-end.

**Files to create:**
- `days-out-code/app/[slug]/setup/page.tsx` — client-side wizard with step indicator
- `days-out-code/app/[slug]/setup/layout.tsx` — no nav bar, no auth guard
- `days-out-code/app/[slug]/api/setup/accept-privacy/route.ts` — sets `setup_progress.privacy_accepted = true`
- `days-out-code/app/[slug]/api/setup/family-name/route.ts`
- `days-out-code/app/[slug]/api/setup/admin-password/route.ts`
- `days-out-code/app/[slug]/api/setup/pin/route.ts`
- `days-out-code/app/[slug]/api/setup/copy-activities/route.ts` — calls `seedActivities(familyId)`
- `days-out-code/app/[slug]/api/setup/memberships/route.ts`
- `days-out-code/app/[slug]/api/setup/complete/route.ts`

Token validation (shared helper used by all setup route handlers):
- Read `?token=` from query string → look up `setup_tokens` (must exist, `is_used = false`, `expires_at > now()`)
- Valid → issue short-lived `setup_session` cookie
- Invalid/expired/used → 404

Step 1: Privacy policy checkbox. "Next" disabled until ticked. On submit → `setup_progress.privacy_accepted = true`. All subsequent handlers check this flag (403 if not set).

Step 5: Calls `seedActivities(familyId)`, shows "70 activities added to your list".

Step 7 (complete): marks token `is_used`, sets `setup_progress.completed_at`, issues full admin session, redirects to `/{slug}/admin`.

Resume banner: on `/{slug}/admin` load, if `setup_progress.completed_at IS NULL` → "Your setup isn't finished. [Resume setup →]"

**Verify:** Operator creates family via CLI → parent completes wizard in <5 min → `SELECT COUNT(*) FROM activities WHERE family_id = ?` → ~70. Abandon mid-setup, re-login → banner shown. Expired token → 404.

## Chunk 7 — PIN Reset + Route Cleanup

**What:** Self-service PIN reset. Redirect old root-level routes. Final cleanup.

**Files to create/modify:**
- `days-out-code/app/[slug]/pin/page.tsx` — add "Forgot PIN?" link below numpad
- `days-out-code/app/[slug]/api/auth/pin-reset/route.ts` — validates admin password, updates `family_pin_hash`, increments `pin_session_version`
- `days-out-code/app/pin/page.tsx` → redirect 302 to `/{atha-family}/pin`
- `days-out-code/app/login/page.tsx` → redirect 302 to `/{atha-family}/login`
- `days-out-code/app/admin/**` → redirect 302 to `/{atha-family}/admin`
- `days-out-code/app/(children)/**` → redirect 302 to `/{atha-family}/`
- `days-out-code/CLAUDE.md` — note that `FAMILY_PIN_HASH` and `ADMIN_PASSWORD_HASH` are retired; credentials now in `family_settings`

PIN reset handler: checks `admin:{familyId}:{ip}` rate limit, validates admin password, bcrypt hashes new PIN, updates `family_settings.family_pin_hash`, increments `pin_session_version`. On next child request, `jwt` callback detects stale `pinSessionVersion` → null → redirect to PIN screen.

Post-delete cache note: after `npm run family:delete`, restart the app container to evict the slug cache: `docker compose restart app`.

**Final verification (go/no-go):**
- `SELECT COUNT(*) FROM activities WHERE family_id IS NULL` → 0
- Auth bypass: admin session for family 1 → request `/{slug-2}/admin` → 403
- PIN reset: reset PIN → old child session invalidated on next request
- Deletion: `npm run family:delete --slug="test-jones"` → counts printed, rows gone
- Old URLs: `/pin` → 302 to `/atha-family/pin`
